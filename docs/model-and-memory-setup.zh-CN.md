# 配置真实模型和员工记忆

[English](model-and-memory-setup.md) | 简体中文

这份指南对应已合入的 Console。免密的确定性演示可以单独部署，但具体地址和部署配置不在
本仓库发布。真实模型的完整前端验收见[带截图的客户反馈教程](scenarios/customer-feedback-deepseek.zh-CN.md)。
保存真实 Key 必须先启用身份认证，并通过 HTTPS 或 SSH 安全通道管理。

## 先理解三个不同的东西

| 配置 | 它是什么 | 是否每个员工都要一份 |
|---|---|---|
| 模型连接 | 模型供应商、模型名称和用于付费调用的 API Key | 不需要；多名员工可以共用连接 |
| 员工版本 | 职责、工作指令、能力、模型连接和工具权限的固定版本 | 每名员工有自己的版本 |
| 公司记忆 | 经过审核、可被后续任务检索的长期知识 | 可以在同一公司内按策略共享 |

“接上 DeepSeek”不会自动带来联网搜索、文件访问或音乐生成。这些是另外的工具能力，需要
单独配置。长期记忆也不是模型厂商的聊天记录，而是 AgentMesh 自己保存并按权限取用的知识。

## 第一个实际场景：整理你提供的客户反馈

这个场景不需要搜索引擎、外部 Memory 服务或付费工具，只需要一个可用模型连接。

例如，你提供 20 条客户反馈，希望得到“主要问题、证据、优先级和回复建议”。准备三名员工：

1. **整理员**：从原始反馈中提取问题与原话，不编造未提供的信息。
2. **分析员**：等待整理员完成，合并重复问题，按影响排序，并说明不确定性。
3. **编辑员**：等待分析员完成，输出你能直接检查的简短报告和回复草稿。

创建任务时填写：

- 目标：分析本周客户反馈，给出优先解决的三个问题。
- 材料：粘贴脱敏后的反馈文本；仅填写电脑上的文件路径不会自动上传文件。
- 预期输出：问题表、对应原话、优先级依据、三条回复草稿。
- 执行方式：多员工协作；为每步选择已发布员工，设置“整理 → 分析 → 编辑”的前置关系。
- 成功条件：每项结论能指向给定材料，缺少证据的推测必须标记，不自动对外发送回复。

先用一名员工跑通也完全可以。拆成三步的价值是职责清晰和中间结果可检查，而不是保证质量
一定高于单个模型。最后一名“编辑员”只是工作流中的一个角色，不等于系统已自动启用
独立审核、反复修订或外部发布审批。

## 管理员先配置一次

1. 开启身份认证，准备管理员访问凭证；匿名演示模式不允许保存真实模型 Key。
2. 在 API 与 Worker 上配置同一个模型连接加密主密钥，并把它保存在数据库之外。
3. 通过 HTTPS 或经过验证的本地/SSH 通道打开 Console；在连接设置中填写平台访问凭证。
4. 添加模型连接，选择 OpenAI 或 DeepSeek，填写模型名称及供应商 API Key。
5. 单独点击连接测试。该操作会请求供应商，可能产生少量费用；“保存成功”不代表连通成功。
6. 创建员工，填写职责和工作指令，绑定连接，然后发布员工版本并设为默认版本。

平台访问凭证与模型 API Key 是两种不同的密钥：前者用于进入 AgentMesh，后者用于调用模型。
不要把任何密钥写进任务、系统指令、员工描述、截图或 Git。

没有域名时不需要急着购买：SSH 可以先提供加密通道。注意，普通 Docker 端口映射可能使
API 看到 Docker 网桥地址而不是本地地址；管理员必须验证部署的通道识别，不能通过关闭安全
检查解决。公网 HTTP 页面不应填写访问凭证或模型 Key。

## 给第二次任务留下有用记忆

第一版使用已有 PostgreSQL 的内置检索，不需要 Mem0、MemOS 或新的 API Key。需要管理员
开启公司与组织记忆功能，并在 Memory 页面选择公司、显式初始化默认策略。

可以先手动添加一条知识：

> 对客户的回复先表示理解，再给出明确下一步；没有确认的修复日期不要承诺。

这条知识先成为候选记录。经授权人员接受后，在下一次任务的高级设置中选择对应的公司
记忆范围，它才有机会被检索并带入员工上下文。未审核、已撤销或不在允许范围内的记录
不应被召回。内置检索是有数量和上下文限制的关键词匹配，不是保证召回的语义数据库。

### 可选的 MemOS Cloud 私有试用

私有试用环境可以用 MemOS Cloud 对本地已经授权的公司记忆做语义排序；普通记忆功能不依赖它。
管理员需要显式开启 `external_memory=true`、指定唯一允许外发的公司 ID、在服务端配置
MemOS Key，并开启远端数据传输开关。默认全部关闭。不要把 Key 写进任务或 Git。

在 Memory 页面先审核接受一条安全的 PUBLIC/INTERNAL 记忆，然后点击
“将已批准记忆同步至 MemOS”并确认。同步会替换该公司的专属远端副本，上限 25 条。
之后运行启用公司记忆的任务即可观察检索。MemOS 不可用时会退回本地关键词排序。
撤销后，本地立即停止召回，但远端副本需要再次同步才能清理。因此当前试用版本不能用于
敏感或受监管的数据。

自动从任务结果提取知识是另一个显式选项，默认关闭。即使开启，提取结果仍需审核；它不会
把每句话都自动变成员工长期记忆。审核可以减少错误知识积累，但不能代替对事实的验证。

## 记忆主题与核实提示

添加公司记忆时，可以填写可选的“主题键”，例如 `release.label-color`（发布标签颜色）和
`release.rollout-thresholds`（推广门槛）。同一事实或决策的版本使用相同主题键。
键会转为小写，允许 1–128 个 ASCII 字母、数字以及 `. _ : / -`，不要包含密钥。
API 的笔记和候选记忆创建也支持 `subject_key`。旧笔记不会被自动猜测主题或改写。

检索结果提供 `conflict_status`、`conflict_reason` 和 `competing_memory_ids`：

- `UNKNOWN`：未填写主题键，尚未判定兼容性，不代表已经发现矛盾，也不代表已批准的规则失效。
- `NO_COMPETING_RECORDS`：同一公司、命名空间、记忆类型和主题下，没有其他不同的有效内容。
  这不是语义正确或绝对一致的保证。
- `REVIEW_REQUIRED`：同主题有不同的有效内容，需要核实，但它们可能互相兼容。
  请审核证据、拒绝错误候选、撤销过时记忆，或通过 `supersedes_id` 提交并批准替代版本。
  系统不会自行选择胜者或覆盖旧记忆。

例如“标签用蓝色”和“推广必须达到毛利门槛”即使同为 DECISION，也不会仅凭内容不同就被判为冲突。
检查基于检索范围内全部已授权的有效候选，在数量和 Token 截断前完成；只展示一条结果也不会
隐藏同主题的其他版本。未审核、已替代、已撤销和已过期记忆不参与检查。
替代版本未填写主题键时继承旧版本；已有主题不能跨主题替换。批准后旧版本同时退役。

每条记忆最多携带 10 个稳定排序的相关 ID；`competing_memory_count` 是完整的已授权数量，
`competing_ids_truncated` 表示 ID 样本被截短，不表示实际记录更少。检索预算同时估算序列化的
记忆内容和元数据，按每 4 个字符一个 Token 向上取整；这不是供应商精确分词或整个提示词的预算保证。

兼容性：旧字段 `conflict` 在 UNKNOWN/REVIEW_REQUIRED 时为 `null`，在
NO_COMPETING_RECORDS 时为 `false`；客户端应改用明确状态。新 Run 会提供核实信息并向员工
说明边界，历史任务快照不会重写。

## 最终交付物与不完整回复

协作任务的“主要交付物”默认使用自动规则：只有一个终点工作项时，它成为主要结果；有多个
终点时，一起展示全部终点产物。你也可以指定其中一个作为主要交付物，其他终点产物仍保留。
中间结果和监督执行记录可以继续查看。

API 创建协作任务时可设置 `output_policy`：

```json
{"mode":"selected","primary_subtask_key":"song","include_subtask_keys":["song","lyrics"]}
```

主要工作项必须是终点。省略 `include_subtask_keys` 时保留全部终点产物。任务完成后，响应的
`deliverables` 与 `primary_deliverable` 提供业务交付物；原有 `output` 保留监督执行结果以兼容
旧客户端。该选择固定在任务输入快照中；未设置规则的旧任务使用自动规则。

模型明确报告因 Token 上限截断时，该 Run 会失败并阻止依赖它的后续工作。请发布输出上限
更大的员工版本，或缩短工作项，然后创建新任务。系统不会自动增加上限或接受截断回复。

## 验收时看什么

- 员工实际执行的版本、模型和任务状态是否与选择一致。
- 每一步是否等待其前置工作完成，以及中间结果能否查看。
- 真实模型输出是否满足你的成功条件；流程成功不等于内容必然正确。
- 开启记忆的任务是否有检索记录，撤销知识后后续任务是否不再召回。
- 供应商测试失败时是否得到安全、可操作的提示，而不是泄露原始响应或密钥。

外部记忆、向量检索、更多模型协议和自动业务操作是可选扩展，不是完成上述场景的前提。
